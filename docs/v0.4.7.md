# Kremen 0.4.7: a first native Windows profile

This release begins Windows support with a defined MSYS2 UCRT64 setup, adds a toolchain self-check, and fixes unnecessary copying in explicit value discards. Linux remains the established release environment. Work and learn keep their existing syntax and safety rules.

## Windows support has a concrete starting point

The first Windows profile targets x86-64 with MinGW-w64 GCC and winpthreads from MSYS2 UCRT64. Building uses the UCRT64 shell and tools; the full-language compiler and generated programs are native Windows executables. WSL is not required.

The new native platform boundary handles process launch, executable discovery, temporary paths, source identity, canonical existing paths, and output replacement. Windows child arguments are passed to the selected program without a command shell. Canonical path checks follow symlinks and junctions before enforcing the project root. Module identity and root comparisons account for Windows case behavior; output protection uses file identity rather than trusting incomplete C-runtime inode information.

The default build name becomes `a.exe` on Windows. Explicit `-o` names remain exact. Runtime discovery follows the compiler's actual executable, and `run` uses the host temporary directory.

This is a staged profile. The initial path APIs use the system code page, so ASCII paths are the predictable starting point. Arbitrary Unicode paths, extended long paths, MSVC, ARM Windows, and the POSIX self-hosted subset are not included. [Windows setup](windows.md) gives the exact workflow and dependency boundaries.

## Check your native toolchain with doctor

```sh
kremen doctor
kremen doctor --cc gcc
```

`doctor` creates a private temporary directory, embeds the actual runtime, compiles a small probe with strict C11 warnings and `-pthread`, and runs it. The probe starts and joins a worker, checking the result. Its files are removed afterward. This catches practical setup problems such as an unavailable backend, a broken compile/link environment, or a program that cannot execute with the expected runtime dependencies.

The command reports the host, compiler, runtime, and successful checks. It accepts `--cc` and `--diagnostic-format=text|json`, with no source path, optimization, root, output, or mode options. A self-check failure uses `E016`; an unreadable runtime uses the existing input error. External C-tool output is still owned by that tool and can accompany the Kremen error.

The probe executes its output. It is not a cross-compiler validator, a complete regression run, or an operating-system sandbox.

## Discard a value without copying its contents

0.4.6 removed unnecessary selected-array copies from fixed-array `len`. Explicit discard statements still had the same kind of problem: `_ = values` could create a full by-value temporary even though the program did not use the contents. Twenty discards of one `[100000]i64` local produced a stack frame larger than 16 MiB at `-O0` and crashed with an 8 MiB stack.

Explicit discards of aggregate places now share the checked place/discard lowering path. Selecting an aggregate name, field, index, or dereference avoids the unused content copy. Entirely ignored tuple destructuring also avoids those copies; partially used tuple patterns retain their ordinary binding behavior. Scalar discard lowering is unchanged. Source expressions still run, calls and indices keep their evaluation order, and bounds, failed-result, stale-slice, null, and conversion checks remain in force. Producer calls and their cleanup cannot be removed just because the final value is discarded.

The common language and learn rules still decide whether a discard is legal. In particular, learn's result-bearing discard checks are unchanged. This is a focused backend correction rather than a general stack bound or a complete IR replacement.

## Preserve filesystem bytes across hosts

The full runtime opens filesystem streams in binary mode. Windows text-mode translation would otherwise change newline bytes or treat `0x1a` as end of input, conflicting with the language's byte strings and file counts. Embedded NUL and control bytes remain data in those streams.

Windows directory creation and file-rename replacement use compatible host operations while retaining result-based error reporting. Metadata uses 64-bit file sizes. File replacement preserves the old target if the move fails, and renaming a file to the same file identity is a no-op. Directory replacement still follows the host's restrictions.

A separate correctness fix keeps `fsWriteAll` from reporting success for an empty write when the stream already carries an error. Empty data does not clear a prior I/O failure. The selected winpthreads implementation supplies the existing integer-worker model; no shared-memory transfer rules are added.

## Installation and validation

The source installer selects the full-language `.exe` profile on Windows and leaves the POSIX subset out. Linux installation still builds and installs both toolchains. Keep the matching frontend, platform helpers, runtime, tests, and documentation together; [repository updates](repository-update.md) lists the complete release changes.

[Validation](validation.md) records the Linux regressions, sanitizer and installation work, and the separate Windows checks. A native Windows smoke test and a Linux regression count answer different questions. Neither establishes support for every Windows version or compiler family.

The original 0.4.7 resource/effect milestone remains future design work. This release prioritizes a usable portability boundary and reproduced correctness problems; it does not introduce effect annotations, generalized ownership transfer, an interactive lesson runner, or a GUI application.
