# Kremen 0.4.6: predictable checking, lowering, and output

This release fixes a generated-stack failure in fixed-array length queries, closes result-discard gaps in `learn`, and makes output failures visible. It also removes repeated checker work on shared type graphs and corrects the input-error explanations in the learning example. `work` remains the default, and both profiles retain the same shared safety checks.

## Query an array's length without copying it

An array's length is part of its type. In 0.4.5, asking for that length still materialized a selected array value as a C temporary. A valid program with one `[100000]i64` local and twenty `println(len(values))` calls therefore created more than 16 MiB of stack storage at `-O0`. It crashed on the release host's 8 MiB stack before reaching its first statement.

The backend now distinguishes a typed computed value from selecting a checked place whose array contents need not be copied. Existing array names, fields, indices, and dereferences can supply their fixed length through this path. The expression still matters: producer calls run, dynamic indices are evaluated once, and bounds, stale-slice, failed-result, null, and integer-conversion checks remain present. A failing expression still runs its deferred cleanup.

Call operands also retain their types alongside their staged C values. Receivers and arguments keep source evaluation order. Builtins stop building an unused serialized argument list. This is a focused internal lowering step; it is not a complete new intermediate representation or a general stack-size guarantee.

## Results cannot disappear inside ignored learning bindings

The original `L002` rule covered local result bindings, tuple destructuring, and explicit discards. It missed other places where a result could be bound and ignored. Learn now also checks:

- Enum payload patterns, including by-value arrays, tuples, and structs containing results.
- Result success patterns that contain another result, such as an ignored `ok` payload of `!!i64`.
- Unread function parameters and by-value method receivers whose values contain results.

An underscore does not waive these requirements. Bind the payload and inspect, handle, or propagate it. The checks apply to loaded function bodies, including imported implementations. External declarations have no body to inspect. Work continues to accept intentional discards under its existing rules.

The analysis still stops at references, pointers, and slice descriptors. Reading a result or its status counts as structural observation; it does not prove a sensible application policy, meaningful handling on every path, or safe handling before every overwrite. [Work and learn profiles](profiles.md) gives the full contract.

## Check shared type shapes once

The shared checker asks whether zero-filled storage would contain an uninitialized result. It previously walked the same by-value type graph again for each local or allocation request. Many locals with one repeated nested type could make a small source file expensive to check.

This query is now cached per type. A targeted check-only regression uses 6,000 locals sharing a legal large type and a command deadline; it does not execute a program with thousands of large stack values. The cache keeps the original zero-state semantics: only an enum's first variant is active during zero initialization. Learn's separate result-discard analysis conservatively considers every variant. Neither rule is weakened.

## Report failed writes instead of silent success

Native output-file failures now use `E015`, with the destination, failed operation, renderer-safe text or JSON, and `kremen explain E015`. This includes parent-directory creation, staging, formatter permission preservation, writes and closes, and final replacement. These failures clean up staging artifacts and leave the previous destination in place. The catalog now contains 45 categories.

Ordinary native commands also check their final stdout flush. A full output device therefore produces failure instead of a misleading successful exit. Bytes already written cannot be rolled back; an executable saved before a failed success message remains saved. Early `--help` and `--version` paths and external C-tool diagnostics retain their existing behavior.

Generated full-language programs check stdout at process termination too. They first join outstanding worker trees and finish resource cleanup, then report `runtime error: output failed during final flush` and exit unsuccessfully if flushing or the stream's error state indicates failure. A delayed flush cannot be attributed to one original `print`, so this report has no source underline. This does not change host signal behavior such as default `SIGPIPE`, or guarantee output after abrupt termination.

## Keep error conventions distinct

The checked-input example previously passed `readIntResult` codes to `errorMessage`. That function describes OS `errno` values; an input-format code could consequently appear as “No such file or directory.”

The example now handles input codes explicitly: `1` for EOF, `2` for invalid format, `3` for an out-of-range integer, and `4` for an input-stream error. Its own `1001` code still means a nonpositive count. Unknown codes are printed numerically. The updated [profile guide](profiles.md) explains why identical integers can mean different things under different error conventions.

## Validation and compatibility

The new suites exercise both profiles, `-O0` and `-O3`, large-array stack behavior, evaluation and deferred-capture order, preserved runtime failures, result-bearing patterns and parameters, bounded shared-type checking, staged-write failures, full output devices, and every input-error case. [Validation](validation.md) records the suite counts, sanitizer commands, clean archive checks, and platform limits.

The strict C flags, integer-worker boundary, borrowing rules, and verified bootstrap compiler seed remain in place. The subset driver's version changes to 0.4.6; it does not gain the full language's profiles or runtime. Install the complete release rather than mixing compiler and runtime files from different versions. [Repository updates](repository-update.md) lists additions and replacements.
