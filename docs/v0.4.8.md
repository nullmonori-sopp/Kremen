# Kremen 0.4.8: native hosts and complete portable packages

This release gives Linux and Windows the same language-facing workflow without requiring a Unix compatibility environment on Windows. It replaces the Windows runtime dependencies, extends path handling to UTF-8 and UTF-16, brings the bootstrap subset to native Windows, and adds packages that carry their own C backend.

The full compiler is still written in C11 and lowers Kremen to C. The smaller self-hosted frontend and CLI remain written in the subset they compile. Work and learn keep their existing syntax, checks, and resource rules.

## One interface, two native implementations

The frontend and runtime now isolate the operations that need host services: processes, threads, file handles, directories, paths, and temporary storage. Linux uses the POSIX interface; a source build normally links its selected system implementation. Windows uses Windows and C-runtime operations directly. There is no Windows pthread-emulation DLL, MSYS2 runtime, or WSL process involved in ordinary use.

The worker API does not change. A named `func(i64) i64` still receives a copied integer; the creator owns its handle, joins it once, and cleans up outstanding children. On Windows the implementation uses CRT-aware thread startup, HANDLE joins, and native synchronization. Worker-local allocation lists and defer stacks keep their existing lifetimes. Linux continues to use the POSIX-thread interface, including the bundled musl implementation for statically linked portable-program output.

This separates platform details from language semantics. It does not make operating-system calls unnecessary or make filesystem permissions, locked files, and signal behavior identical on both hosts.

## Unicode belongs at the host boundary

The compiler keeps paths and arguments in UTF-8. On Windows it reads the original wide command line, converts paths to UTF-16 for native operations, and converts directory names back to UTF-8. Source files, imports, temporary directories, process arguments, and filesystem built-ins use this boundary.

Normal Unicode paths no longer depend on the current ANSI code page. Invalid encodings and embedded NUL are rejected. Existing source paths are still resolved through handles before checking the project root; file identity still protects source and toolchain resources from case and hard-link aliases.

Recursive module-loading buffers are allocated from the compiler arena rather than multiplied on the Windows stack. This matters for long import chains even when every individual path is short. Host path and namespace limits still apply; the change does not promise every extended-length Windows path or an unpaired surrogate filename will work.

## Unpack a compiler and its backend together

A portable archive contains `bin/`, `share/`, and `backend/`. It carries the full compiler, the native bootstrap driver, their matching resources, documentation, examples, and a complete Zig 0.15.2 SDK. The small `backend/bin/clang` launcher forwards separate arguments to `zig cc` without a shell.

Unless `--cc` or `CC` selects another compiler, Kremen discovers this backend relative to its executable. A complete package therefore compiles programs offline without requiring GCC, Clang, Visual Studio, MSYS2, or WSL to be installed separately. Temporary and compiler-cache storage must still be writable.

Linux release binaries are static, and the bundled backend selects the static `x86_64-linux-musl` target for generated programs. This removes a dependency on the host's glibc ABI. The result still targets a compatible Linux kernel and CPU; it is not a universal executable for every operating system.

The SDK is a bundled C backend, not a replacement implementation of the Kremen frontend. Its license material remains in the package. A source archive is a different artifact and still needs development tools to build Kremen itself. Read [Portable packages](portable.md) before copying individual executables or redistributing a package.

## Native Windows development and bootstrap

Windows source builds use PowerShell, native Clang, and the Windows SDK. The full compiler can be built with `build.ps1`; `selfhost/bootstrap.ps1` builds the subset stages and verifies the committed C seed against successive generated C files. The subset driver supports `check`, `emit-c`, `build`, `run`, and its own verified rebuild on both hosts.

This is still a smaller language. Moving its existing host primitives to Windows does not add the full language's modules, results, borrowing, or worker API to that frontend. Full-language self-hosting and a direct machine-code backend remain separate projects.

The subset also stops treating failed standard output as a successful command. This matters for redirected version/check reports and programs built by the subset. After cleanup it checks both the final flush and the stream's error flag. A previously successful command becomes unsuccessful; an existing nonzero status is preserved. The late report is plain text without a source underline, because buffering prevents attributing the failure to one original print. The subset does not adopt the full frontend's JSON diagnostics.

The Windows installer uses an ownership manifest and a selected prefix. It copies a complete portable package or prepared source build, preserves unrelated files, and supports removal through `-Uninstall`. Linux retains its source installer. See [Installation](install.md), [Windows setup](windows.md), and [Self-hosting](selfhosting.md) for commands and prerequisites.

## Validation and boundaries

The new runtime cases exercise Unicode files and directories, binary streams, native worker creation and joining, nested cleanup, invalid handles, and handled worker failure. Backend tests check argument transport and package construction; a fixture SDK used by a transport test is not evidence that real code compiled. The separate portable checks compile and run programs with the real bundled SDK, clear inherited compiler overrides, move the package, and remove development compilers from `PATH`.

The native Windows checks use PowerShell and Clang rather than MSYS2. Linux keeps its semantic, diagnostic, sanitizer, installation, bootstrap, and archive regressions. [Validation](validation.md) records the commands and distinguishes these kinds of evidence.

The supported distribution targets are Linux x86-64 and Windows x86-64. Other architectures, every historical OS version, arbitrary foreign C libraries, freestanding kernels, and a universal shared-memory transfer model are not established by this release. The common borrow and runtime checks remain active; portability does not create an unchecked mode.
