# Kremen 0.4.4: explanations and semantic fixes

0.4.4 is a small stabilization release and the first step toward the planned teaching tools. It adds useful help to the existing compiler, corrects rejected valid expressions, and improves source locations and command validation. It keeps the current language and worker model.

## An explanation without opening a browser

Run `kremen explain E131` after a borrow error, or `kremen explain --list` to see the 39 native diagnostic categories. Each explanation describes the reason, gives concrete things to check, and includes an example. The catalog is compiled into the executable. It needs no project, runtime header, C compiler, account, or network connection.

Text diagnostics print the corresponding command. JSON diagnostics gain an additive `explain` field with that command, or `null` when no explanation exists. Read the specific error first: codes describe categories, and one category can cover several checks. The [error guide](diagnostics.md) explains the interface.

There is no `work`/`learn` switch or lesson runner in this release. The [roadmap](roadmap.md) describes that work as planned, rather than exposing empty modes before their rules and tests exist. The explanation catalog is the first part that those tools can reuse.

## Correct integer context around calls

The checker previously rejected an expression such as `1 + object.tiny()` when `tiny` returned `i8`, although the corresponding named local function worked. Its preliminary type lookup did not find the method's result, so the literal fell back to `i64` and produced a false mismatch.

Result hints now include imported functions, value and borrowed methods, nested method calls, and more builtins. The hint pass only discovers types; argument evaluation, borrow checking, and other validation still happen in the ordinary expression pass. Calls execute once, in source order. Regression fixtures check the inferred `i8` type by passing the value to an `i8` parameter and comparing all observable output.

This does not introduce implicit integer conversions. `128 + aCallReturningI8()` remains outside the `i8` literal range, and adding an existing `i64` variable to an `i8` result still requires an explicit conversion.

## Mark the type that needs fixing

An unknown type now marks its annotation rather than the declaration's `var` token. Qualified annotations carry the whole source range. Spelling suggestions for `vec.Vectro` search the imported module and can suggest `vec.Vector`; they do not invent a qualified primitive such as `vec.bool`.

More command failures use the same diagnostic renderer: unknown commands, wrong source counts, invalid formatter modes or extensions, invalid formatter stdin, and output paths that would replace a source or toolchain resource. Formatter stdin shares the source NUL validator, including byte-accurate CRLF locations.

Late OS failures, external C-compiler output, formatting-drift reports, and program runtime output still have their existing formats. The frontend still reports the first error. The self-hosted subset keeps its separate diagnostics.

## Less repeated formatting work

The compiler formats short internal strings once into a bounded stack buffer, then copies the result into its arena. Longer strings retain a checked allocation and second formatting pass. Boundary, long-string, variadic-argument, UTF-8, and embedded-zero tests check that the returned bytes are preserved.

The new emitter comparison uses the same 3,000-function input with 0.4.3 and 0.4.4, alternates their order, and requires byte-identical generated C. Saved timings vary across rounds; they do not establish a guaranteed speedup. See [benchmarks](../bench/README.md) for the script, raw results, and measurement limits.

## Validation and source updates

The regular suites contain 419 checks: the previous 390 plus 29 stabilization checks. ASan/UBSan cover the new compiler helper, diagnostics, and generated inference fixture as well as the preceding suites. The 16 thread-runtime scenarios also run under ThreadSanitizer. Installation tests exercise the explanation command before and after prefix relocation.

CI derives archive names from `VERSION`, verifies their checksums, and builds both toolchains from a fresh extraction into a path containing spaces. [Validation](validation.md) records the commands and limits. [Repository updates](repository-update.md) lists the files added and changed since 0.4.3.

The runtime, verified C bootstrap seed, and bootstrap compiler source retain their 0.4.3 contents. The subset driver's version string changes, but it does not gain full-language features. Existing safety checks and strict C flags remain enabled.
