# Kremen 0.4.9: integer math and steadier code generation

This release adds a small library that real programs can import, reduces unnecessary copies in pattern matching, and makes strict warnings easier to interpret. The new regression cases focus on integer boundaries, source-loading boundaries, diagnostic records, and the behavior of generated programs.

Linux x86-64 and Windows x86-64 keep the native workflows introduced in 0.4.8. The full frontend remains C11 and lowers Kremen to C. The self-hosted subset keeps its smaller language. Work and learn use the same library, source rules, runtime checks, and backend defaults.

## A first bundled library

Use `import "std/math"` to access eleven integer operations: `min`, `max`, `clamp`, `magnitude`, `abs`, `add`, `mul`, `gcd`, `lcm`, `pow`, and `isqrt`.

The library is ordinary Kremen source with a paired `.krh` API. It performs no allocation and uses no `unsafe` block or native math library. `gcd` uses Euclid's algorithm, `pow` uses repeated squaring, and `isqrt` uses a bounded integer search. The library is included in source installations and both portable packages, and imports require no network access.

Functions that can encounter an unrepresentable answer or invalid input return `!i64`. They report codes `2001` through `2004` for overflow, reversed clamp bounds, negative exponent, and negative square-root input. These are library-specific codes, separate from OS errors. `magnitude` and `gcd` return `u64`, allowing them to represent the magnitude of the smallest `i64`.

The [math guide](math.md) walks through an import, a successful call, and explicit failure handling. It also documents `gcd(0, 0)`, `0^0`, zero-input `lcm`, and the smallest signed integer. Floating point, trigonometry, generics, and a broad standard library remain outside this release.

## Library imports keep their own source boundary

The reserved `std/` prefix resolves sources from the compiler's installation. A project's `std/` directory cannot shadow those modules, and using the library does not require a wider `--root`.

Ordinary relative imports remain inside the selected project root. Standard-library files and automatically paired headers remain inside the separately resolved library root. Directory members and symlink targets receive canonical boundary checks. Malformed standard paths are rejected. A missing library reports `E013` with a repair hint; moving only the compiler executable does not create a complete installation.

The source layout is `stdlib/math/`. Installed and portable layouts use `share/kremen/stdlib/math/`. Move `bin/`, `share/`, and the portable `backend/` together, as described in [Portable packages](portable.md).

## Match existing values without copying everything

Previously, every `match` first copied its whole subject into a temporary, even if every arm ignored a large payload. Repeating that operation could create a large stack frame in an unoptimized build.

The backend now resolves an existing variable, field, indexed element, or dereferenced subject through its checked address. It reads the discriminator once and copies the named payload bindings before any source code in the chosen arm runs. An ignored payload needs no value copy. A call or other expression that produces a new enum or result still has its ordinary temporary value.

Pattern bindings retain value semantics. Replacing the original subject inside an arm does not change a binding already captured from it. Subject expressions still run once, and index evaluation, bounds checks, stale-slice checks, failed-result checks, and deferred cleanup retain their behavior.

In the local GCC 14 `-O0` regression, twenty matches on an enum containing a 100,000-element `i64` payload reduced the reported stack frame from 16,800,352 bytes to 800,352 bytes. The previous generated program failed under an 8 MiB stack limit; the updated program completes. At `-O3`, the C compiler already removed these copies in the measured case. This is evidence for a smaller debug-build stack requirement, not a guaranteed speedup for every release program.

## Fatal warnings are clear to people and editor tools

JSON diagnostics now include two additive fields:

| Field | Meaning |
| --- | --- |
| `severity` | `"warning"` for warning categories, `"error"` for other categories |
| `fatal` | `true`, including warnings that make the command fail |

The existing `kind:"error"` field remains unchanged for compatibility. Text output keeps `error[W001]` and adds a note explaining that warnings are treated as errors by default. Both work and learn retain the strict policy; no warning-suppression switch is introduced. The offline catalog still contains 46 categories.

Unused `var` and `const` diagnostics now underline the binding's identifier instead of the declaration keyword. Related notes for an earlier binding also select its name. Inferred declarations and parameters keep their existing identifier locations.

Read [Understanding errors](diagnostics.md) for the full fields, byte ranges, rendering rules, and the distinction between frontend, C-backend, and runtime output.

## Validation and remaining work

Math tests cover success and failure boundaries in work and learn at `-O0` and `-O3`. Code-generation tests exercise large subjects, copied bindings, side effects, safety failures, and cleanup. Import tests exercise packaged sources and source boundaries. Installer and portable checks run a program that imports the shipped math library.

[Validation](validation.md) records the executed suites and host results. A focused benchmark or regression is useful evidence for its own case; it does not establish universal performance or complete program safety.

This release does not add a lesson runner, project-profile file, floating-point type, full-language self-hosting, direct machine-code backend, or shared-memory threading model. The [roadmap](roadmap.md) keeps those separate from the implemented work.
